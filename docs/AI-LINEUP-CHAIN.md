# AI 布阵学习：完整链路与「是否海量数据集」

> 本文回答两个问题：**现在的 AI 优化是不是靠海量数据集**；以及**从一局真人布阵到别的服务器用上它**，
> 数据到底经过哪些环节、每个环节的默认值与阈值是什么。

## 一、结论先说：不是海量数据集，是「小窗口候选库 + 模拟择优」

| 维度 | 实际做法 | 海量数据集路线（未采用） |
|---|---|---|
| 数据量 | 每个库**最多 4000 行 / 3 MiB**（约 4000 条布阵，≈ 0.7 KiB/条），按「玩法 + 难度」分文件各自滚动 | 百万级样本、离线训练 |
| 学习方式 | **不训练模型**。AI 整备时把记录到的真人布阵当作**额外的试算候选**（默认方案 + 参数化变体之后最多再给 2 条），交战斗模拟择优 | 训练策略网络 / 价值函数 |
| 变强机制 | 只有模拟打得赢现有候选才会被选中 ⇒ 伪造/劣质布阵无法让 AI 变弱，最坏是浪费一次试算 | 依赖数据质量与训练稳定性 |
| 生效对象 | 同 `modeId + stageId + difficulty + round` 的检索键命中才用，其余情况完全走原逻辑 | 全局泛化 |
| 失效代价 | 库读不到/写失败 = AI 回到默认布阵，对局照常 | 需回滚模型 |

所以「海量」不是当前方案的前提；它要的是**近期的、同场景的、真实的**布阵，量在几千条量级就够。
真要走向海量数据集，缺的是：离线聚合（当前只有 4000 行滚动窗口）、特征化与训练管线、以及中心侧的
重算/抽样校验（现有的 `SP_VERIFY` 只覆盖战斗结果，不覆盖布阵质量）。

### 每个环节的默认值（当前 3 个分支一致）

| 环节 | 默认 | 变量 |
|---|---|---|
| 形态 | `local`（记录 + 上传） | `SP_LINEUP_MODE`（`local` / `public` / `off`） |
| 库目录 | `<repo>/lineups`（镜像内 `/app/lineups`） | `SP_LINEUP_LIBRARY` |
| 上传目标 | `https://downcdn.jiangjiangze.icu`（R2 前置） | `SP_LINEUP_PUBLISH_URL` |
| 上传口令 | `CDN_ADMIN_KEY` 或 `~/.cdn_admin_key` | 同左 |
| 上传时机 | **结算后立即**（3 秒合并窗口）+ 15 分钟兜底 | 无（内置） |
| 只读侧地址 | R2 稳定别名 → GitHub 镜像 | `SP_LINEUP_MODE=public` 或自定义 `remote:<urls>\|<cacheDir>` |
| 滚动窗口 | 4000 行 / 3 MiB | 常量 `MAX_LINES` / `MAX_BYTES` |

### 「只能上传训练文件」的边界（审计发现）

服务端专用通道 `/api/lineup/*` 强制：`source=lineup-library` 时键必须是
`packs/lineup-library/*.jsonl`，其它落点一律 400。**但同一个上传口令仍能走主通道上传素材** ——
也就是说「只能传训练文件」目前约束的是**这条通道能传什么**，不是**这把钥匙能做什么**。
要真正做到钥匙级隔离，需要在后台签发一把只允许 `lineup-library` 来源的口令（未实施，属 CDN 仓改动）。

## 四、当前方案的已知缺口（审计结论）

1. **密钥未做通道级隔离**（见上）：同一口令可走主通道传素材；要严格「只能传训练文件」需后台签发限定来源的口令。
2. **窗口只有 4000 行**：这不是缺陷而是取舍（近期性 > 总量）；若要「海量」，需要离线聚合与训练管线，当前没有。
3. **中心侧不校验布阵质量**：只做形状校验（越界/朝向/规模），信任模型是「rehearsal 自限」；胜负/资源数字不在本链路里传。
4. **冻结超时的对局一行不写**（`abandoned` 被门控挡掉）：与「异常素材不要」一致，但意味着长时间断线的局学不到东西。
